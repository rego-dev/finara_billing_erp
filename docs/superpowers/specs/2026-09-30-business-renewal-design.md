# Business Renewal (Recurring Payment for Business Orders)

## Goal
A business's own users can pay to extend that business's `paidUntil` before or after it lapses, from the My Businesses page — the same manual payment-proof review model as a new-business order, just applied to an existing business instead of creating a new one.

## Decisions
- Self-service: any user with access to a business (owner, or `ADMIN`/`SUPER_ADMIN`) can initiate and pay for its renewal — not admin-initiated.
- Always available, not gated on nearing/past expiry. Extension stacks: if `paidUntil` is still in the future, the new period is added on top of it; if it has already lapsed, the new period starts from today. Either way computed by the existing `computePaidUntil(from, period)` helper, just with a different `from`.
- Company type for pricing is derived from the business's own order history, not re-asked or re-typed: `BusinessOrder.companyType` already stores the real plan-pricing key (e.g. `SERVICES`), unlike `Business.industry` which only stores the display label. No schema change. A business with no order on record can't renew (see "Renew" visibility below) — consistent with it also having no `paidUntil` to extend.
- A renewal order's company snapshot fields (`companyName`, `tin`, `address`, `phone`, `taxType`) are taken from the **current** `Business` row at renewal-order time, not from the original creating order — the business may have been edited since (via Settings > Businesses) and the renewal should reflect that.
- One open renewal order per business at a time — creating a second while one is `PENDING_PAYMENT`/`PROOF_SUBMITTED` is rejected (409), so a customer can't stack two payments for the same renewal. A business can still have both an open new-business order and an open renewal order concurrently (unrelated purposes); the guard only compares renewals against the same `businessId`.
- "Renew" is shown whenever `Business.paidUntil` is not null — that alone implies the business has at least one linked order to price from (paidUntil is only ever set by an approved order). No extra API call is needed just to decide whether to show the button.
- No automatic/unattended billing, no expiry reminders/notifications, no admin-initiated renewal, no grace-period/auto-suspend on lapse. All out of scope.

## Backend
- New shared helper `server/utils/businessAccess.js` exporting `assertBusinessAccess(user, businessId)`: throws `createError('Access denied to this business', 403)` unless the user is `ADMIN`/`SUPER_ADMIN` or has a `UserBusiness` row for that business. Extracted from the inline check currently duplicated at the top of `businessController.get`; that controller is updated to call the new helper instead of repeating the check.
- Two new routes in `server/routes/orders.js`, alongside the existing user-facing (non-admin) routes, reusing the `businessId` numeric-id guard already added for the business-detail admin route:
  - `GET /orders/renew/:businessId` → `orderController.renewQuote`. Calls `assertBusinessAccess`, loads the business (404 if missing), finds its most recent `BusinessOrder` (`orderBy: { createdAt: 'desc' }`, take 1) to read `companyType`; 409s with "This business has no order on record; it cannot be renewed here" if there is none. Returns `{ companyType, prices: <active MONTHLY/YEARLY PlanPrice rows for that companyType>, instructions: <same shape orderController.plans() already returns> }`.
  - `POST /orders/renew/:businessId` → `orderController.renew`. Body: `{ period }`. Calls `assertBusinessAccess`, loads the business (404 if missing), re-resolves `companyType` the same way as `renewQuote` (never trusts a client-sent value), validates `period` against `PERIODS` and the resolved `PlanPrice` (mirrors the validation already in `orderController.create`). 409s if an OPEN order already exists for this `businessId` (`prisma.businessOrder.findFirst({ where: { businessId, status: { in: ['PENDING_PAYMENT', 'PROOF_SUBMITTED'] } } })`). Creates a `BusinessOrder` with `businessId` already set to the target business (this is the one place besides `orderAdminController.approve` that ever sets it), snapshotting `companyName`/`tin`/`address`/`phone`/`taxType` from the current `Business` row, `companyType` from the resolved order, `period`/`amount` from the resolved price, `booksStartDate: null` (not applicable to a renewal). Returns the created order (same shape `orderController.create` returns).
- `orderAdminController.approve`: after the existing atomic claim (`updateMany` to `APPROVED`), branch on whether the claimed order already has `businessId` set:
  - **Set (renewal):** load the business, compute `newPaidUntil = computePaidUntil(business.paidUntil && business.paidUntil > new Date() ? business.paidUntil : new Date(), order.period)`, `prisma.business.update({ where: { id: order.businessId }, data: { paidUntil: newPaidUntil } })`. No provisioning call, no rollback-on-failure path (there is nothing to roll back — the business already exists). `recordAudit` with a renewal-specific summary (e.g. `Approved {orderNo}; extended "{business.name}" to {newPaidUntil}`). Response: `{ message, businessId }` (same shape as today, so the admin page's existing success toast works unchanged).
  - **Null (new business):** exactly the existing flow, unchanged.
- No Prisma schema changes.

## Frontend
- `lib/api.js`: add `orders.renewQuote: (businessId) => api.get(\`/orders/renew/${businessId}\`)` and `orders.renew: (businessId, period) => api.post(\`/orders/renew/${businessId}\`, { period })`.
- New `components/orders/RenewBusinessModal.jsx` (props: `business` — `{ id, name, paidUntil }` — and `onClose`, `onDone`), self-contained, following the same modal-chrome pattern as `AddBusinessModal`/`BusinessDetailModal`:
  - On mount, calls `orders.renewQuote(business.id)`; on failure (e.g. the 409 "no order on record" case) shows a toast and calls `onClose()`.
  - Step 1 (compose): shows the business name and current paid-until date, a period picker (Monthly/Yearly, same as `AddBusinessModal`), and the resulting price for the chosen period from the quote's `prices` list. Submitting calls `orders.renew(business.id, period)`, then moves to Step 2 with the created order.
  - Step 2 (payment): identical in content and behavior to `AddBusinessModal`'s existing payment step (payment instructions text, QR image via `ordersApi.qrBlob()`, reference number input, proof file upload, submit via `ordersApi.submitProof`) — duplicated rather than extracted into a shared component, matching how `BusinessDetailModal` already duplicates modal chrome instead of sharing it with `AddBusinessModal`.
- `app/(dashboard)/my-businesses/page.jsx`: add a "Renew" button in the Businesses table, shown whenever `b.paidUntil` is not null (regardless of role — unlike the `SUPER_ADMIN`-only "View" button). Opens `RenewBusinessModal` with that row's `{ id, name, paidUntil }`; `onDone` reloads the page's data the same way `AddBusinessModal`'s `onDone` already does.
- The page's existing "Orders" table needs no changes — a renewal `BusinessOrder` renders there identically to a new-business one (same `STATUS` badges, same Pay/Update payment/Cancel buttons), since that table only reads generic order fields already present.
- `admin/orders/page.jsx` (admin review queue) needs no changes — it already lists/approves/rejects any `BusinessOrder` generically.

## Testing (Jest, existing style)
- New `tests/businessAccess.test.js` (or folded into an existing suite touching it): `assertBusinessAccess` allows `ADMIN`/`SUPER_ADMIN` unconditionally, allows a user with a matching `UserBusiness` row, throws 403 otherwise.
- `tests/orderController.test.js`: add cases for `renewQuote` (resolves `companyType` from the latest order, 409 when no order exists, 403 via the shared helper, 404 for unknown business) and `renew` (creates an order with `businessId` pre-set and the current business's snapshot fields, 409 on an existing open renewal order, rejects an inactive/missing price the same way `create` does).
- `tests/orderAdminController.test.js`: add cases for `approve` branching — a renewal order (businessId set) extends `paidUntil` from the business's current value when still in the future, extends from today when lapsed, and never calls `createProvisionedBusiness`; a new-business order (businessId null) behaves exactly as today's existing tests already assert (no change to those tests).
- `tests/businessGetAccessControl.test.js` (existing file covering `businessController.get`'s access rule) needs no changes — it exercises `get()` through `prisma.userBusiness.findUnique`/`prisma.business.findUnique`, the same calls `assertBusinessAccess` makes internally, so it keeps passing unchanged as a regression test once `get()` delegates to the new helper.
- No frontend test suite exists in this repo — `RenewBusinessModal` and the My Businesses page changes are verified via `npm run build:prod`, consistent with the rest of this codebase's frontend testing (or lack thereof).

## Out of scope
Automatic/unattended recurring billing, expiry email/notification reminders, admin-initiated renewal on a customer's behalf, grace-period or auto-suspend behavior when `paidUntil` lapses, changing company profile fields as part of renewing (that's what Settings > Businesses > Edit is for), letting a business change its company type at renewal time.
